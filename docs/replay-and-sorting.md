# 长列表排序与直播回看（2026-10-01）

> 2026-10-02 更新：小马最终选择约三分钟内存回看，刷新、换画质、关闭房间或重启后重新积累。FLV 按最新已缓存位置滚动清理，暂停时仍淘汰旧内容；浏览器配额不足时缩短实际范围。进度条使用固定尺度、可见时平滑更新、拖动松开才寻址。下面保留此前修复记录与持久缓存分析，磁盘持久缓存未实施；当前实现和验证见 [多窗口性能方案](multi-room-performance.md)。

来源：桌面 `New 2.txt` 的两个问题。先记录方案，再修改代码。

## 本轮修复

- 排序改用指针拖动，避开浏览器原生 HTML 拖放对滚轮的限制。拖动时滚轮立即滚动列表；接近上下边缘时按距离加速滚动，滚动后重新计算插入位置。保留预览、标记、方向键和上下按钮。松开提交一次；Esc、失焦、切换视图或结束编辑取消，取消不改排序。
- 平台房间明确按直播显示，不再仅凭 `video.duration` 判断。直接文件仍支持点播时间；直接 FLV 按直播处理，直接 HLS 从播放清单确认直播/点播。
- FLV 播放器明确 `isLive: true`，关闭点播式 lazy-load，避免回看或暂停积累约三分钟后主动断开取流。现有 ReactPlayer 2.16 创建 FLV 时没有传入该参数，也没有暴露 FLV 配置，因此只替换 FLV 适配，HLS 与直接文件继续用原播放器。
- FLV 回看仅在当前真实 buffered 范围内跳转，避开被清理的旧数据与断开的空档；HLS 沿用可寻址范围。返回直播使用最新范围末端，不被当前所在的旧范围限制。
- 内存缓冲采用 FLV 常规滚动清理：正常观看时超过约三分钟的历史触发清理，保留约两分钟；浏览器仍可能因内存不足更早清理。回看/暂停时保留窗口还受播放位置与浏览器配额影响，不能承诺固定分钟数。刷新、换画质或关闭画面卸载播放器会丢失这份缓冲。
- 实测发现 FLV 1.6.2 自带 Fetch 加载器在 Chromium 缓冲阶段会等下一个数据块才中止连接，卡住的流在关闭房间后可能还挂着请求。通过公开 customLoader 接口提供可立即 Abort 的 HTTP 流加载器，连接十五秒、接收连续无数据三十秒报错；正常收到数据会续期，用户关闭或换流直接中止，不触发旧房间错误回调。WebSocket 流继续使用库内对应加载器。

## 半小时本地缓存的分析与建议

目前没有独立的本地录像层。浏览器媒体缓冲不能跨播放器重建或网页刷新保存；扩大 MSE 内存到半小时也不能解决持久化问题。

建议后续作为独立、默认关闭的本地回看功能实施：

1. 以平台和真实房间号为键，保存压缩音视频分片、初始化片段、关键帧及墙钟时间索引到浏览器 IndexedDB 或 OPFS。FLV 要将接收到的数据转为可重播的片段；HLS 可保存分片及对应播放清单。不能只缓存含有效期的直播 URL。
2. 每个房间只保留最近三十分钟的实际时间范围，并增加所有房间合计的容量上限；磁盘配额不足时先淘汰最旧数据，提示实际剩余回看范围，不能让写入失败打断正常观看。按 8 Mbps 计算，半小时约 1.8 GB；16 Mbps 约 3.6 GB，多房间会累加。
3. 房间在布局中时，接收直播和回放互相独立：回退后播放本地片段，直播继续写入滚动缓存；暂停也继续接收。点击返回直播切换到最新可播放位置，不重建整个房间。
4. 关闭房间、关闭布局或网页后立即停止接收；保留已存片段。再次打开先连接当前直播，仍可回看尚未淘汰的片段；若关闭超过三十分钟，按上述时间窗口淘汰过期片段。浏览器自行清理站点数据、用户清缓存或换端口/浏览器后不保证仍可用。
5. 断流、退出布局、换画质及时间戳重置都形成独立会话段。时间轴显示真实空档，拖动到空档时跳到最近可播放边界并提示，不能把不存在的视频显示成缓存。跨段播放必须重新加载匹配的初始化片段，处理编解码器和分辨率变化。
6. 自动卡流恢复只重建实时连接，已有磁盘分片仍保留；回看中的故障和实时接收故障分别处理。需验证关房间即停止网络、刷新后恢复、连续回看写入、跨空档/画质切换及容量不足。

这需要独立的录制、存储淘汰和回放适配，不能通过一个缓存时长参数完成。本轮完成当前排序和回看故障修复、验证与文档分析，不把尚未实现的持久缓存写成已有功能。

## 追加说明：滚动窗口与中断后的观看体验

以下仍是持久缓存的建议设计，尚未实现，也不意味着所有行业播放器都有同样的跨空档操作。

- 常见直播时移方案以几秒一片的媒体分片和播放清单工作，已完成的分片就能回放，不必等整半小时录完。随着新分片进入，最旧分片从回看窗口退出；半小时满了不会全清空重录。
- 连续接收时，20:30 的窗口约为 20:00～20:30；到 20:35 变为 20:05～20:35。左边界前移，不在当前进度条左侧留下越来越长的空白。
- 多看建议沿用同一个房间播放器和进度条，回看读本地分片，接收直播继续进行。重开房间默认连当前直播，可往左访问尚未过期的历史；不让用户挑选底层分片文件。
- 一直开着房间，底层也已经是许多小分片。断流/关闭后恢复，只是新增一个连续会话的边界；旧分片不覆盖，新旧仍挂在同一房间的一条时间轴上。
- 20:00～20:10 录到 A，20:10～20:12 关闭或断流，20:12～20:20 录到 B：显示 A、灰色两分钟空档、B。建议 A 播完自动跳到 B，并提示跳过两分钟；不等待两分钟、不补黑色视频。可以自动连续观看已录内容，但跨段可能短暂加载，不能保证完全无感，也不能补出没录到的视频。
- 当前正在读取的少量分片需暂缓物理淘汰，防止读到一半删除；该保护有界，不无限延长缓存。若暂停太久导致播放位置过期，恢复时提示并移到最早仍可播放的位置。
- 延续此前建议：三十分钟按真实时间窗口计，容量不足可更短；关闭房间后停止接收，过期数据下次打开时清理，不需要在关闭期间维持后台录像。这项保留策略属于多看的产品选择，并非 HLS 标准强制规则。
- 行业依据：[AWS MediaPackage 时移窗口](https://docs.aws.amazon.com/mediapackage/latest/userguide/time-shifted.html)；[HLS RFC 8216](https://datatracker.ietf.org/doc/html/rfc8216) 支持滚动删除旧清单条目，并以 discontinuity 标记时间戳、轨道等变化。上述自动跨空档、提示和本地存储由多看自己实现，标准标签不会自动完成整套体验。

## 追加问题：斗鱼实时观看音画不同步

小马确认：正常实时观看也出现，主要为斗鱼，声音先到、画面晚到；尚未测试仅开一个房间的情况。

- 即使源内容同步，浏览器侧转封装、时间戳校正、解码与显示仍可能出问题。刷新重建这些状态可以暂时恢复，但单凭刷新有效不能确定哪一层出错。
- 已确认本项目 Windows 默认使用 FLV。上一版 ReactPlayer 使用 FLV 1.5.0；本轮改为独立 FLV 1.6.2 直播适配。当前 `fixAudioTimestampGap` 默认已开启，不能把重复开启该选项当作新修复。转封装仍在主线程，不能把容器缩小等同于降低视频源解码负担。
- 优先区分两种候选：多房间/高帧率时的视频解码或显示落后，以及 FLV 音视频时间戳处理产生偏差。声音领先画面符合前一种症状，但目前没有丢帧、解码耗时或时间戳异常记录，不认定为硬件性能问题。
- [flv.js #241](https://github.com/bilibili/flv.js/issues/241) 与 [#194](https://github.com/bilibili/flv.js/issues/194) 有旧版本正常直播逐渐不同步、时间戳补偿相关报告，只作为调查方向，不能据此认定多看当前实例的根因。
- 下一步应在同一房间对比单房间/多房间、普通画质/最高画质，采样视频丢帧、呈现帧时间、解码耗时与 FLV 时间戳补偿日志。[帧回调](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback) 和 [丢帧计数](https://developer.mozilla.org/en-US/docs/Web/API/VideoPlaybackQuality/droppedVideoFrames) 可提供证据，但不直接测量声音与画面内容的同步误差。
- 不因回看距直播较远而强制返回直播，也不在正常观看时定时刷新掩盖偏差。卡流监控当前判断时间/帧是否推进，不能识别“仍在播放但音画偏离”；未把音画同步问题标记为已修复。

## 追加问题：多开卡顿与原始项目对比

小马反馈多个房间一起观看时明显卡顿，并询问原始项目是否也会发生。以下为源码检查结果，尚未做相同房间、相同实际画质下的两个版本性能对照，不能把可能的负载因素写成已确认的卡顿根因。

对比基线为本地 `upstream/main` 的 `7cfce1f`，未联网确认上游是否已有更新。

| 路径 | 原始项目 | 当前多看 | 对性能的含义 |
| --- | --- | --- | --- |
| 多路播放 | 每个房间一个 ReactPlayer，持续播放 | 每个房间一个播放器；聚焦缩略窗口仍持续播放 | 多路视频接收、解码与合成的成本两者都有，缩小窗口或静音不会等比例降低解码成本 |
| 默认画质 | 默认原画；斗鱼向接口请求 rate=0 | 默认最高可用，按房间返回的 bit 选最高码率 | 标签相近不代表实际流相同；当前版本有可能选到比原版更高的档位，比较必须核对实际分辨率、帧率和码率 |
| FLV 转封装 | ReactPlayer 2.16 默认加载 flv.js 1.5.0，未传 Worker 配置 | 独立 flv.js 1.6.2，未开启 Worker | FLV 解析和转封装仍在页面主线程，多路会累加；它与浏览器的视频解码是不同工作 |
| 弹幕接收 | 视频和弹幕分别添加 | 新房间默认开启并自动连接弹幕 | 当前默认观看可能比原版承担更多弹幕消息解析、布局和合成工作 |
| 弹幕空闲循环 | 弹幕引擎即使无消息仍每帧运行，读取容器宽度 | 沿用同一循环；此前只增加字号设置 | 属于继承的可优化开销，未测量其占比，不能认为它单独解释严重卡顿 |
| 播放条与状态 | 浏览器原生播放控制，没有当前的时间轴上报 | timeupdate、progress、durationchange、seeked 更新房间时间轴，重渲染该窗口 | 当前新增了界面开销；时间轴更新本身不会每次重渲染整个工作区，但缓冲恢复的 playing 会写播放状态和历史，引起更大范围更新 |

原始项目同样可能在多开、高分辨率或高帧率下达到资源瓶颈，但没有实测证据证明其一定卡顿，或其卡顿程度与当前多看一致。当前版本增加的开销也必须单独检查，不能全部归因于上游或机器性能。斗鱼声音领先画面的反馈与视频侧负载偏高相容，也与时间戳问题相容，仍未定位。

建议的排查顺序：

1. 在生产 START 页面保持同一组房间、同一布局与弹幕设置，对比一个房间和多个房间；多开时逐个关闭画面，观察画面掉帧和页面操作迟滞是否一起改善。DEV 有额外开销，但不能假定换生产模式就一定解决。
2. 手动把非主要观看房间选为较低分辨率/帧率的实际档位，再单独关闭弹幕做对照；只调整窗口大小不构成解码负载对照。每次只改变一个因素，不静默改动用户偏好。
3. 采样每路视频的呈现/丢帧数量、解码耗时，以及页面脚本、布局耗时；画面卡而页面操作流畅与整个页面操作迟滞需要区分。小型本地视频功能测试不能证明真实高码率多开性能。
4. 如果确认页面开销，优先消除弹幕闲时循环与无变化状态更新，把时间轴刷新限制在需要它的控制区域；如果主要是源视频解码负载，再讨论可选的非聚焦房间画质策略。功能设计与性能测量先记录，再按证据改代码。

不能只添加 `enableWorker: true` 就宣称解决：当前 HTTP customLoader 是构造函数，flv.js 初始化 Worker 时会传输整个配置，函数无法 structured-clone，会失败并退回主线程。Worker 方案必须兼容即时取消和超时加载器，再做实际验证。

本次只追加分析文档，未修改播放策略或性能实现，未提交、未推送。现有功能验证结果不代表多开性能验收。

## 追加方案：多开画质策略与回看冲突

小马询问降低码率、改画质、按窗口大小自动调整的取舍，以及普通布局、聚焦/全屏和回看如何共存。以下为建议方案，尚未实现或测量效果，不改变当前画质偏好。

### 应降低什么负载

- 对多路视频解码，优先选择平台提供的较低分辨率、较低帧率档位；相比仅降低压缩码率，降低每秒要处理的像素数量通常更能减轻解码和合成压力。码率主要影响带宽、数据处理与缓存大小，同分辨率/帧率的低码率不保证解码成本明显下降。实际效果还取决于编码格式和浏览器硬件解码是否启用。
- 网页无法通过一个参数把正在接收的原画源直接变成低码率流；需要重新向平台请求已有的另一档。浏览器收到原画后只缩小显示尺寸，仍需解码原画；在客户端自己转码也不是当前适合的省资源方案。
- 当前斗鱼画质列表只保证 name、rate 和可选 bit，没有统一的分辨率/帧率元数据，不能把“高清/原画”标签或码率直接当作准确的 720p/1080p/30fps。自动规则必须按平台实际提供的档位降级，并检查已播放视频的分辨率，不能承诺平台没有的档位。
- 消除弹幕闲时循环、冗余状态更新和控制区域之外的时间轴重渲染，属于可保留源画质与当前缓冲的优化方向；仍需要性能采样确认占比。即使完成这些优化，也不能保证机器能同时解码任意数量的最高画质房间。

### 可选的省资源模式

建议作为独立、默认关闭的设置，普通布局也有明确规则，保留逐房间手动固定画质。用户的画质偏好与当前自动选择的实际档位分开，临时降档不覆盖用户偏好。

| 观看状态 | 建议策略 |
| --- | --- |
| 普通布局 | 自动房间按稳定后的实际视频显示尺寸选择适合的档位，可先以平台提供的约 720p 档作为常见多开对照；大窗口选更高，小窗口选更低，不把所有普通窗口都锁为最低档 |
| 聚焦 | 主窗口恢复用户选定的画质上限；周围缩略窗口选择较低档位 |
| 全屏 | 目标房间恢复用户选定的画质上限；其他房间按省资源规则运行 |
| 手动固定画质 | 普通布局、聚焦、全屏均服从用户选择；不能自动覆盖，取消固定后再进入自动规则 |
| 暂停或回看 | 锁定当前播放器，聚焦、全屏、缩放均不自动切流；返回直播后才重新评估 |

“恢复高画质”是重新获取并播放较高档位的直播源，可能短暂加载；原画本身也经过有损压缩，因此应称为恢复所选原画/最高可用，不能承诺无损或瞬间切换。回看低画质片段时进入全屏，只会放大已有片段，不能生成未接收的高清细节。

窗口大小是选档依据之一，不能每次拖动或逐像素变化都换流。需要在尺寸稳定约一至两秒后评估，跨越有间隔的升降档阈值才切换，同档不重连，并避免快速切换聚焦/全屏引发连续请求。仅按大小选档也不能保证解决所有多开负载，还需验证实际丢帧、帧率与系统资源情况。

### 当前回看会怎样

已核对 `loadStream`：实际换流后增加 `playbackKey`，PlayerAdapter 重建播放器，FLV 旧实例 destroy。当前回看仅存在该播放器的媒体缓冲中，因此换画质会丢失旧缓冲，从新连接重新积累；备份 URL 只能恢复原档连接，不能恢复已销毁的缓存。取流请求在切换前失败时可以保留原播放器，这与已完成切流后的缓冲丢失不同。

所以仅增加“回看时不自动切流”仍不够：它能保护正在回看的位置，但实时观看中自动换档也会清空此前积累、随后可能想回看的内容。在独立缓存层完成前，不建议默认按窗口大小频繁自动切换。可以先手动给次要房间设置固定较低档位，之后维持该连接积累回看；再次换档仍会重置缓存。

### 持久缓存实现后的处理

- 延续半小时缓存方案：换档形成同一房间时间轴上的新会话段。旧片段保留原画质，新片段记录新档位，各自使用对应初始化数据；编解码器、分辨率、时间戳变化需显式处理。多看负责跨段播放，可能短暂加载，不能拼接文件就宣称无缝。
- 例如 20:00～20:10 接收 720p、20:10 聚焦后接收 1080p，回看前十分钟仍为 720p，后段为 1080p。新连接等待期间未接收的内容仍是空档，不能补成完整缓存，也不能让旧片段恢复未录到的原画。
- 如要“平时低画质看，始终原画回看”，需要另外持续接收高画质录制源并保存，而低画质源用于显示。录制压缩媒体可以不解码高画质视频，但会增加连接、带宽、解析/转封装和磁盘成本；不是低成本兼得的方案，当前不推荐默认实施。

当前建议顺序：先验证并降低不影响画质/缓冲的页面开销，再用固定低档位对照多开效果；独立缓存和跨档回放可靠后，再启用可选自动画质。此次只记录方案，未添加自动降档或持久缓存代码，未提交、未推送。

### 针对多看的建议顺序

1. **先保留各房间当前源画质。** 采样一个、多个房间的主线程脚本/布局耗时、实际分辨率/帧率、呈现与丢帧，以及浏览器实际使用的解码器；不要把窗口变小、静音或换 Electron 当作解码优化。用同一斗鱼房间、同一档位比较浏览器与原生播放器的持续观看，区分源/时间戳与浏览器播放链路问题。
2. **减少多看自身开销。** 弹幕无待处理消息及活跃条目时停 rAF；尺寸通过 ResizeObserver 更新；减少逐条写 DOM 后测量产生的布局；时间轴更新限制在播放控制区域并合并重复上报；重复 playing 不重复写入相同播放状态与历史。这些是确认存在的开销路径，其实际占比仍未测量。
3. **独立验证新 FLV 内核和 Worker。** 优先对照 mpegts.js 的转封装/MSE Worker 与现有 flv.js，在相同流和画质下比较页面流畅度及长时间同步。必须验证 Worker 确实运行、关闭/换流立即断开 HTTP、连接与无数据超时、失败后的资源释放、暂停/声音/全屏/现有回看，不能只看配置字段为 true。
4. **按同步证据修复。** 分别记录 AAC 时间戳补偿、音视频时间基准异常和视频丢帧/呈现落后。帧回调的 mediaTime 与公共播放时间差能反映候选呈现问题，但不能精确测量声音内容相对画面内容的偏移。flv.js 当前 fixAudioTimestampGap 已默认开启，重复开启不是新修复。
5. **硬件瓶颈再讨论产品取舍。** Worker 迁移的是脚本与媒体缓冲工作，无法减少原画视频必须解码的像素/帧数量。若浏览器硬解没有生效，先解决硬解/编码兼容；若硬解已经饱和，评估独立原生播放后端，或者让用户固定选择较低档位/减少同时播放数量。原生方案是架构扩展，不立即重写多看。

mpegts.js 仍有两个需要专门处理的兼容点：其 Worker 初始化同样发送整个 config，当前 customLoader 构造函数不能 structured-clone；读取的 Fetch loader 也仍有 Chromium 缓冲期延后 abort 的条件分支。不能把直接换依赖、删除定制加载器或打开 Worker 开关视为完整解决方案。应保留即时取消与超时语义，再验证 Worker 适配。

此外，[MDN HTTP/1.x 连接管理](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Connection_management_in_HTTP_1.x) 说明浏览器常见每域六个并行连接限制。多个长连接 FLV 若落在同一 HTTP/1.x CDN，新增房间可能排队；应从真实请求协议、等待阶段和域名确认。HTTP/2 可多路复用，但 CDN 是否支持不由网页单方面决定；这只是待检查项，不能用它解释所有已在播放的音画偏差。

### 顺滑换画质的适用条件

[hls.js 的切换说明](https://github.com/video-dev/hls.js/issues/5334) 区分立即切换、后续分片切换与保留已有缓冲的保守切换。配合服务端提供时间轴/关键帧对齐的多档播放清单，后续分片改档可以避免重建整个播放器；画质变化会晚一些才显示。即时切换也可能清缓冲或出现呈现停顿。

当前平台接口按房间和档位返回独立直播地址，尚未确认存在可供客户端统一切换、时间轴对齐的多档 HLS master playlist。不能仅把协议改为 HLS 就承诺无缝，也不能把任意两个 FLV 连接拼进同一个缓存即视为可靠切换。因此暂不以频繁自动换源解决多开问题。

mpegts.js 的 liveSync 调整整体播放速率、liveBufferLatencyChasing 跳向较新缓冲，解决的是距直播位置的延迟，不等于修复音画内容偏差；回看、暂停不应被强制拉回直播。原生帧调度方案也必须区分显示丢帧和解码丢帧，不能承诺跳过显示就显著节省所有解码成本。

本次完成来源核对和方案更新，尚未进行真实多房间性能对照，也未修改播放内核、自动换档、时间戳或资源调度实现。临时独立 3037 生产测试服务已停止；原有本地修改继续保留，未提交、未推送。
